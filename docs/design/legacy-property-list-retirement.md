## 改修前に確認したこと

- 現行入口は `app/app.vue` → `app/components/MeetingPrototype.vue`。fetchRowsは物件一覧にpropertyList、保証案内にlist＋alertKind=warranty／notification=pending、保険案内にlist＋alertKind=insurance、保険報告にlist＋reportMonth／includeDoneを送る。請求・保証書は専用billingList／certificateListを使う。
- `functions/property-warranty.js` の汎用listは、会社・状態・自由語・各種日付等の条件があるとlimit20を外す。しかし月・保証番号以外の多くは取得後にmatchesPropertyで絞るため、HSでは全物件、工務店利用者では所属内全物件の取得になる。
- `functions/warranty-notice-query.js` と `functions/insurance-notice-query.js` の最適化対象は現行HS画面の条件だけ。対象外要求にはnullを返し、呼出側が従来検索へ進む。準備不備時のHS通常案内は既にエラー停止へ改修済みで、今回の残件ではない。
- 保証のdone/all、自由な追加検索、旧日付範囲出力の操作は現行画面にない。一方、businessNavigationは工務店利用者にも保証満了案内を表示する。工務店側を単に「未使用の旧入口」として削除できるとは判断しない。
- 旧条件は `test/emulator/property-warranty.test.mjs` 等でも使われている。試験呼出しの存在は現行画面の必要条件を意味しないが、削除によって既存業務の試験範囲を失わないよう置換が必要。
- Devの旧クライアント・外部呼出しの稼働状況は今回未調査。リポジトリで現行呼出元がないことと、実環境で呼ばれていないことは区別する。

## 採用：受け付ける一覧条件を限定し、汎用の全件取得を撤去

専用Callableや新画面を追加せず、既存propertyPrototypeOperationの要求を取得前に分類する。対応外条件で従来取得へ進む分岐をなくす。未対応を空一覧として成功させず、明示的に拒否する。

| 入口・条件 | 採用した動作 | 互換性 |
| --- | --- | --- |
| propertyList：条件なし／保証番号完全一致 | 現在どおり最新20件／完全一致。会社・本支店の所属制限を維持 | 現行画面不変 |
| list：条件なし／warrantyNumberのみ | propertyListと同じ取得処理へ内部で振り分ける。新たな全件取得はしない | 安全な旧呼出しは維持 |
| list：保証pendingのみ | HSは既存候補検索。工務店／本支店も以下の所属付き候補検索へ | 現在画面の条件を維持 |
| list：保険alertKindのみ | HSの既存候補検索。工務店利用者は現在どおり権限エラー | 現行画面不変 |
| list：reportMonth＋任意includeDone／warrantyNumber | 現在の月別対象検索を維持。includeDoneは真偽値、保証番号は完全一致 | 全物件走査ではないため撤去対象外 |
| list：billingMonth＋任意warrantyNumber | 現在の月一致検索・返却を維持。現行請求画面へ無条件に置換しない | 旧請求と現行請求では未処理繰越等の意味が異なるため、旧月検索の整理は別件 |
| 保証notification=done/all、通知条件省略、案内への追加条件、自由語・工務店等・状態・年度・日付範囲・旧from/to出力、条件の混在、未知のキー | 物件取得前にinvalid-argument。「この検索条件には対応していません。画面を再読み込みしてください。」等の既存エラー表示で停止 | 旧要求への互換性終了を承認済み |

filter未指定は空条件として扱う。filterを指定する場合は配列・null・文字列を拒否し、オブジェクトだけ受理する。許容キーを確認してから値を検査する。未知キーは値が空でも拒否し、既知の空保証番号のみ従来どおり条件なしとして扱う。復元用・表示名省略等の上位項目をfilterと混同しない。認証と復元制限の既存処理順序・境界は維持する。

この案はdone/all等の検索機能を新設・拡張する案ではない。将来必要となった条件は、業務要件とDB取得条件を定めて個別に追加する。任意の条件を受け取り全件読んでから絞る共通処理へ戻さない。

## 工務店側の保証案内

アカウント一覧の後発対応とは分け、現在存在する保証案内の読取りを限定する。

1. 認証済みアカウントから会社ID・担当範囲・本支店IDを確定する。検索要求のIDから権限を決めない。必要な所属IDが欠落・不正なら拒否し、HS範囲へ広げない。
2. 既存のwarrantyNoticePending=true、expiryDateの開始時基準上限に、会社担当ならconstructionCompanyId一致、本支店担当ならさらにbranchId一致を加える。
3. 準備情報の取得前後確認、開始時の案内月数・日本日付、検索項目欠落の非救済、返却前の復元世代確認をHS経路と共用する。未準備時は全件取得へ戻さずエラー。
4. 候補取得後の保証対象判定、updatedAt欠落除外、秒・ナノ秒・ID順、返却項目を維持する。工務店向け表示項目制限と既存名称解決も維持する。UIからのomitReferenceLabels指定で認可・表示制限を外さない。

追加索引は、会社＋warrantyNoticePending＋expiryDate、会社＋本支店＋warrantyNoticePending＋expiryDateの2構成をfirestore.indexes.jsonに追加する。実装の検索条件と定義を照合し、導入時には索引準備完了を確認する。索引不足を全件取得で回避しない。

取得件数は所属内の未案内候補数に比例する。無関係な他社物件や対象外物件が増えても増えないことを検証し、対象候補自体が増えた場合まで一定件数とは説明しない。画面の段階取得・対象全体のCSV分離は今回の範囲に入れない。

## 影響範囲・データ整備・差戻し

- 主対象：`functions/property-warranty.js` のlist分岐、`functions/warranty-notice-query.js` の権限範囲付き候補取得、`firestore.indexes.json`。必要なら条件分類を小さな関数へ切り出す。insurance-notice-queryは呼出条件の検証を確認し、候補計算を変更しない。
- 現行画面の要求形は維持できる見込み。画面項目追加・検索候補追加は不要。月別一覧、請求・保証書、業務の保存・採番・共有Store・アカウント管理は変更しない。
- 検索項目は既存値を共用するため、新たな物件項目・ID移行・業務データ移行は不要。既に必要とされる保険検索等の導入前整備は別工程のまま維持する。工務店経路も準備不備時に停止する点は旧動作との差分として仕様へ反映する。
- 採用時に仕様・満了案内要件・検索要件・設計・工程・判断記録・運用／利用説明を更新する。オーナー採用に基づき拒否方針を確定仕様へ反映する。
- 導入時は現行クライアントの要求形とサーバー対応を照合し、旧条件を使うクライアントが判明した場合は更新または機能廃止の扱いを決める。無期限の全件検索互換は設けない。Devの調査・配備は明示指示後。
- 差戻しは本件取得・条件判定部分だけ。追加索引は残せる。データ書戻しは不要。旧方式へ戻せば全件取得が再発することを明記し、先行した欠落非救済・本支店コード・保証延長等の変更を一括で戻さない。

検証条件：

- 許容条件の一覧結果・順序・返却形を維持。条件なしは20件まで、保証番号は古い物件でも完全一致検索できること。
