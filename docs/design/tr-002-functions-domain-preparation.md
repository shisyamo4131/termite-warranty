# TR-002 Deterministic Functions Domain Preparation

- Status: Implemented and accepted
- Date: 2026-09-12
- Roadmap: [TR-002](../roadmaps/technical-remediation.md#tr-002-make-shared-domain-code-deterministic-for-functions)
- Baseline: `bd4f90df93aad9b865d2a420374b0b3c07d425ae` on `codex/tr-002-functions-preparation`

## Objective

Make `src/domain` the only authored copy of Firebase-independent domain modules while ensuring every supported Functions consumer prepares and verifies an exact generated copy at `functions/domain` before loading Functions code.

## Current Behavior and Risk

- Nuxt, local seed scripts, and domain tests import `src/domain` directly.
- Deployable Functions import `functions/domain` because Firebase deploys the configured `functions` source directory.
- `functions/domain` is ignored and generated by `scripts/prepare-functions-deploy.mjs`.
- Firebase predeploy and `npm run test:rules` prepare the copy, but `npm run emulators:start` and the registered Functions syntax command can use a missing or stale copy.
- The preparation script replaces the directory but does not independently prove that the resulting relative file set and bytes equal the source.

## Required Design

### Authoritative and generated paths

- `src/domain` is authoritative and remains committed.
- `functions/domain` is generated and remains ignored.
- Preparation paths are resolved relative to the repository scripts, not the caller's current working directory.
- Only regular files and directories are accepted under the authoritative source. Symbolic links and unsupported filesystem entries fail preparation or comparison rather than being followed implicitly.

### Deterministic preparation

Provide one reusable implementation that:

1. recursively enumerates the source using sorted repository-relative POSIX-style paths;
2. copies into a unique staging directory under `functions`;
3. verifies that the staged relative file set and file bytes exactly match `src/domain`;
4. replaces `functions/domain` with that verified stage;
5. verifies the final generated directory again; and
6. cleans its own stage after success or failure.

Concurrent preparation uses one exclusive lock in `functions`. A waiter retries for a bounded period, then rechecks the generated output and returns without replacement when the first process already produced an exact copy. Timeout fails closed and preserves the existing generated directory; an abandoned lock is not deleted automatically.

An explicit comparison command must fail on a missing, extra, or byte-different generated file without silently repairing it. Preparation may repair drift by replacing the whole generated directory, but must verify the new result before succeeding.

### Required invocation paths

- Add `npm run prepare:functions` as the canonical preparation command.
- The documented `npm run emulators:start` command prepares first through its npm lifecycle hook.
- `npm run test:rules`, which contains the maintained Callable integration tests, prepares first.
- The registered Functions syntax command prepares before loading or checking Functions files.
- Firebase Functions predeploy invokes the canonical npm command.
- Directly invoking Firebase CLI Emulator commands outside the documented npm command is not a supported prepared path.

### Testing

Unit tests use temporary directories and prove:

- a missing destination is created exactly;
- stale and extra destination files are removed by preparation;
- comparison rejects missing, extra, and byte-different files;
- nested relative paths and binary bytes are compared without newline normalization; and
- concurrent preparation serializes replacement and leaves one exact generated copy; and
- unsupported source entries are rejected where the host permits creation of the fixture.

The real-path comparison command and Functions syntax command provide repository-level evidence after preparation.

- affected operations, roadmap, design-index, and changelog text

## Explicit Non-goals

- Do not change any domain business rule or authored file under `src/domain`.
- Do not change Callable behavior, Firestore Rules, schema, UI, seed data, or dependencies.
- Do not close TR-003 by expanding syntax coverage or changing the development deployment workflow's verification gates.
- Do not implement TR-007 or alter the current master Callable boundary.
- Do not deploy or contact a live Firebase project.

## Completion Contract

- Removing `functions/domain` and invoking each registered Functions consumer recreates an exact copy automatically.
- A standalone comparison detects missing, extra, and changed generated content with a nonzero exit status.
- Generated and staging content is excluded from commits.
- Existing domain, Callable, application, and governance behavior remains unchanged.
- The roadmap and operations documentation name the canonical preparation and comparison paths and record measured validation.

## Required Validation

Run each command separately and record its exit status against the final worktree:

1. `./scripts/check-governance.ps1`
2. `npm test`
3. `npm run prepare:functions`
4. `npm run check:functions-domain`
5. `node scripts/check-functions-syntax.mjs`
6. `npm run typecheck`
7. `npm run build`
8. `npm run test:rules`
9. `node --check scripts/seed-emulator.mjs`

The clean-copy rehearsal may remove only the ignored generated `functions/domain` directory before rerunning the canonical commands. No external deployment is authorized.

## Rollback

Revert the TR-002 implementation commit. `functions/domain` contains generated data only and can be regenerated by the prior predeploy script; no application or Firestore data migration is involved.
