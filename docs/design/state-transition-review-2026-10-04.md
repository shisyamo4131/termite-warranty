## 状態を分けて考える

1つの物件に単一の進捗状態を置くのではなく、対象と期間を分ける。内部登録済みと、日付到来による期間開始も別である。未来の引渡日で本登録しても、登録操作日から保証が始まったとは扱わない。

| 管理対象 | 単位と状態 | 他の対象へ自動反映しないこと |
| --- | --- | --- |
| 物件・保証の存続 | 下書き／本登録／取消。番号は恒久 | 取消を保険会社・請求先への外部取消と同一視しない |
| 保証期間 | 初回10年、各10年延長、最長20/30年 | 延長で保険期間や請求実施結果を進めない |
| 保険報告 | 対象の5年区間、初回／更新、報告記録 | 未報告を無保険、報告済みを補償成立の証明としない |
| 保証満了案内 | 対象の保証満了日に対する未案内／案内済み | 別の満了日へ案内済みを無条件に流用しない（提案） |
| 請求 | 新規加入1件・各延長1件ごとの未請求／請求済み（採用待ち） | 請求済みを入金済みと扱わない。物件全体の1フラグにしない |

通常の保険適用開始日は引渡日という説明がユーザーから確認済みで、翌月報告の前に開始する。報告操作はその外部実施をHSが記録するもの。過去物件の未適用区間・初期取込は別途HSC-036の判断が必要で、画面の未報告だけから実際の補償を断定しない。

## 推奨する遷移と影響範囲

以下の「提案」は未採用。外部への実際の通知・請求・報告はHSが行う前提を維持する。

| 操作 | 内部で変わるもの | 維持するもの／注意点 |
| --- | --- | --- |
| 本登録（通常新規） | 恒久番号、初回保証10年、初回保険5年の予定区間、未報告、未案内 | 請求管理採用時のみ新規加入の未請求項目を作る。登録≠保険報告・請求実施。過去物件の初期取込区間は別途判断 |
| 初回保険報告の記録 | 特定の初回区間を報告済み | 保存済み期間は変えない。CSVを出すだけでは遷移させない |
| 保険更新報告の記録 | 特定の次区間へ連続5年進め、その区間を報告済み | 保証期間は伸びない。何回先まで実施するかを一操作で曖昧にしない |
| 保証満了案内の記録 | 対象満了日の案内済み | 保証・保険・請求は変えない |
| 案内記録の取消 | 同じ満了日を未案内へ戻す | 外部で送った案内を自動撤回しない |
| 保証延長 | 保証期間を10年追加、新満了日を未案内 | 保険は変更せず次回の更新対象を再判定。請求管理採用時は延長の未請求項目を作る |
| 保証延長取消 | 直近の有効な延長を無効化、保証期間を復元 | 保険保持は既決。案内は同じ満了日へ戻る場合だけ旧状態復元を提案。請求済みなら消すだけでなく外部訂正の確認が必要（採用待ち） |
| 保険報告の記録取消 | 特定の直近操作前の区間・報告状態を復元 | 単純に5年減算しない。外部提出済み内容の訂正完了を意味しない |
| 請求の記録／取消（提案） | 対象の加入・延長1件の請求状態 | 金額・入金管理は追加しない。請求済み記録を戻しても発行済み請求書は消えない |
| 物件・保証全体の取消／復元 | 本登録と取消を切替 | 保険・案内・番号を保持。取消中は業務抽出から除外、復元時は保持状態で再判定。対外訂正の未完了を消してよいかは別問題 |
| 引渡日訂正 | 許可条件内で保証・保険期間を再計算 | 満了日が変わる場合の案内済みリセット／再確認を提案。初回報告取消の要否・一度更新後の通常編集禁止は現行維持 |

保険期間が保証期間を超えていても、それだけで破損とは扱わない。過去物件や延長取消後に保険の余剰期間が残ることは既決の運用であり、保険満了を保証満了へ自動短縮しない。

## 食い違い・不足の優先順位

### 1. 対象満了日が変わっても案内済みが残る（交差条件の仕様不足）

現行の[引渡日訂正](../../functions/property-warranty.js:229)は保証満了を再計算するがwarrantyNotifiedを維持。[延長取消](../../functions/property-warranty.js:269)も延長前の案内状態を日付照合なしで復元する。

例：保険未報告など引渡日訂正が許可される状態で、2036-09-30の満了案内を済ませる→延長→引渡日を2026-10-01から2026-10-06へ訂正→延長取消。保証は2036-10-05満了へ戻るが、2036-09-30に対する案内済みが復活する。未案内一覧から外れる可能性がある。

既存[試験](../../test/emulator/property-warranty.test.mjs:368)は2回延長・引渡日訂正・2回取消を含み、旧案内済みの復元を期待している。コードの実装漏れだけではなく、承認済みの「延長前の状態へ戻す」を交差条件まで広げてよいかという判断が必要。

最小提案：満了日訂正時は未案内へ戻す。延長取消は履歴のbefore.expiryDateと戻す満了日が同じ場合だけ案内状態を復元し、異なるなら未案内。既存履歴を利用でき、全案内履歴の新設を必須にしない。所有者だけの訂正をリセット対象にするかはこの提案から推測しない。

前回答の「不整合なし」は日付訂正を挟まない復元試験の範囲。本レビューではより広い業務上の整合性まで保証できないことを明記する。

### 2. 提出した内容と報告済み操作が固定の組になっていない（外部実施との照合不足）

[CSV出力](../../app/components/MeetingPrototype.vue:250)はダウンロードだけで出力対象を保存しない。[報告済み](../../app/components/MeetingPrototype.vue:240)はその時点で選択中の行ID/revision/月を送る。画面の同じ取得結果に対する同時編集はrevisionで防ぐが、CSV出力→実際に提出→別作業で内容変更→再検索→報告済み、という別時点の内容の取り違えを機械的に検出できない。

最小提案：報告確認に初回/更新、適用対象となる開始・満了日を明記し、HSが提出した内容と照合する。さらに保証するならCSV対象と期間を固定した提出単位の記録へ報告操作を結び付ける（追加仕様、未採用）。全報告履歴を持たない既決方針との調整が必要。CSV保存だけで自動的に報告済みにする案は採らない。

### 3. 同月に再抽出すると別の5年区間を処理できる（区間識別不足）

[insuranceReportKind](../../src/domain/property-warranty.mjs:80)は現在区間と指定月で対象判定し、報告操作は5年進める。複数期の遅延なら同じ対象月で再抽出するたび、まだ対象となる別区間が出る。初回区間の満了月では初回報告→同月の更新報告となる場合もある。再送防止が効かないのではなく、異なる新規操作として有効になっている。

例：現在保険2026-10-06〜2031-10-05、保証2046-10-05まで、指定月2036-10。更新後に保険2031-10-06〜2036-10-05となり、同じ月の再抽出でもう1期対象。ドメイン関数を直接評価してpast-renewal→renewal→対象外を確認（サーバーやDevへの書込みはしていない）。将来年月の指定も現行は禁止していない。

遅延分を順番に報告する業務なら合理的だが、1件の外部報告で2期進めてしまわない確認が必要。期間を明示した1操作・HSの実施確認とする案。初回区間をまたぐ過去物件の処理は既にHSC-036で未確定、安全側でreview扱いとなる場合がある。

### 4. 請求済み・未請求と請求対象区間がない（既知の未採用範囲）

[billingRows](../../src/domain/property-warranty.mjs:115)は新規/延長のイベントを抽出するのみ。CSV出力で請求済みへ変わらず、請求済み・請求記録取消の保存状態もない。これは[HSC-010](../requirements/house-solution-confirmations/HSC-010-payer-contracting-party.md)の確認待ちであり既存実装の欠陥と断定しない。

また抽出イベントは個別だが、表示/CSVの保証期間は現在の物件情報。同月に新規と2回延長すれば3行とも現在の30年間が表示され、後日の延長で過去年月の再出力も変わる。画面は「現在の保証期間」と表記しており、請求対象の10年区間を示す確定要件はない。

提案：請求管理を採用するなら、初回と各延長のIDに対象区間・請求状態を対応させる。請求対象月は操作月か延長区間開始月か別途決める。CSV再出力≠再請求。請求済み延長を取り消した場合は請求の訂正が残ることを把握できるようにする。金額計算・入金管理を自動的に追加しない。

### 5. 記録の取消と、外部で実施した業務の訂正が同じ入口（意図的簡略化）

現行は警告文でHSへ訂正連絡を委ねる。実際に報告していないのに誤って報告済みにした場合と、提出後に報告内容を撤回する場合を別状態で追跡しない。延長取消後は請求一覧から対象が消え、物件取消中も通常抽出から外れるため、外部訂正の作業漏れは検出できない。

「記録ミスの訂正」と「実際の報告/請求を訂正する必要がある場合」を運用で分けるのが推奨。最低限はHSが別管理する対象・担当・完了確認を決める。システムに訂正対応待ち/完了を追加するなら別途採用が必要で、過去に保留/履歴を省いた決定を無断で覆さない。

## 現行と一致している点・残すべき制約

- 初回は引渡日起算、保証10年・保険5年。保証延長は保険報告に自動連動しない。
- 保険更新は前満了の翌日から5年。初回報告では日付を変えない。
- 延長取消は保険を保持し、取消履歴を残し、該当延長だけ請求一覧から除外する。
- トランザクションとrevisionは同時変更を、requestId/receiptは同じ要求の再送を防止する。外部提出の重複や異なる操作IDでの業務上の重複まで保証するものではない。
- 取消中は報告・報告取消・案内変更を拒否。復元は既存状態保持。実際の外部状態と一致するかはHS対応が必要。
- 保険報告取消は直近1回の保存状態へ戻し、以前の取消用情報は再生しない。初回→更新→更新取消後、さらに初回報告取消はできない。全履歴を持たない現行の簡略化で、連続遡及取消は未採用。
- 一度でも保険更新後は、報告取消しても引渡日ロックを維持する。
- 保証上限到達時の保証/保険アラート要否はHSC-036の既存確認待ち。20年保証でも15年時点の保険継続が要る場合があり、上限到達だけで保険予告を消さない。

## 次に決める順序（未採用の相談案）

1. 案内済みを特定満了日に限定し、満了日訂正では未案内へ戻すか。
2. 外部報告/請求の訂正対応をHSの別管理で完結させるか、システムで最小限の対応待ち/完了を持つか。提出内容との照合方法も決める。
3. 請求の済/未済を初期対象へ追加するか。追加するなら取引単位・対象月・取消条件をHSC-010で確定する。

採用後は、案内済み→日付訂正、2回延長→日付訂正→順次取消、初回と更新が同月、複数期の遅延、CSV提出後の再編集、請求済み延長取消、全体取消→復元を組合せ試験する。単純なボタン単位の試験だけでは足りない。
