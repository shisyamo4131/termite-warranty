## R1の保存と検索

- saveGroup／reenableMaster(group)の全グループ取得を `where('prefix','==',prefix)` へ変更。limitなしで一致文書のみ取得し、自分以外のIDがあれば拒否。有効／無効の絞込みはしない。
- 検索と保存は既存の同じrunTransaction内。今回初めてトランザクション化する変更ではない。既存ID、本体の更新、権限、復旧制限、接頭辞／年度開始月の固定、通常編集の後勝ちを維持する。
- 入力前後空白の除去は維持し、末尾ハイフン除去を撤去。`HSC` と `HSC-` は別物。空接頭辞も完全一致で比較する。専用予約、検索用追加項目、管理コレクション、準備印は作らない。
- 同じトランザクションで対象一致検索を行う設計の根拠はFirestoreの直列化可能性。Functions自身が順次実行されるとは仮定しない。[公式説明](https://firebase.google.com/docs/firestore/transaction-data-contention#serializable_isolation)。本実装の同時登録は独立接続で実証してから完了を判断する。

## 番号と既存データ

新しい番号は保存接頭辞＋区切りハイフン＋年度＋通番とする。`HSC`→`HSC-26-001`、`HSC-`→`HSC--26-001`、空欄→`26-001`。既存の末尾ハイフン付きグループも今後の新規採番はこの規則を使う。保存済みwarrantyNumberは再計算・書戻ししない。CSVや画面の新規採番も共通関数で同じ規則を使う。

グループIDや参照先の移行、使用先記録の生成は不要。導入前にprefixの保存形式を読取り確認し、欠落／空白／不正値と末尾ハイフン付きグループを報告する。既存仕様では入力時にtrimしているが、正規処理外の値を推測補完しない。実データの現在件数・不整合は未調査。発行済み番号・グループ設定・採番値はそのまま保持する。

## 影響と差戻し

製品変更は `functions/property-warranty.js`、共通の `src/domain/property-warranty.mjs`。編集画面は同じ共通関数を使うため、旧末尾ハイフンを削らず表示・送信できる。Functions配布用domainは既存生成手順に従う。保存形の追加・Firestore Rules・索引・依存・環境設定変更は不要。

番号生成の解釈が変わるため、従来版へ無条件に差し戻すと `HSC` と `HSC-` を再び同一扱いし、今後の採番形式も戻る。新規番号／新設グループを保全し、検索方式だけ全件比較に戻す場合も完全一致と末尾ハイフン保持を維持した修正版にする。既存番号を変更して帳尻を合わせない。Dev導入・差戻しとも今回未実施。

## R2・R3：本支店／CSVの採用設計

2026-10-13、オーナーが本案を採用し実装・検証を指示。[元の調査](full-read-audit-2026-10-12.md)。Dev反映は未承認。

### 改修前の読取りと採用方式

本支店コードの管理記録 `branchCodeReservations` は既に存在する。会社IDとコード全文から算出したキーで、会社・コード全文・本支店IDを記録し、本支店の保存／無効化／再有効化と同じtransactionで更新している。今回、新しい使用先記録は作らない。

| 対象 | 改修前 | 採用方式 |
| --- | --- | --- |
| R2 本支店保存・再有効化 | `functions/property-warranty.js` の `reserveBranchCode` で変更前後の管理記録を取得し、非空コードを有効として保存するときは同一工務店の本支店も全件取得 | 管理記録による重複判定と同時更新を維持し、同一工務店の全件検索だけ撤去 |
| R3 CSV事前確認・確定 | `functions/property-bulk-import.js` で同一工務店の本支店全件と、CSV内の異なるコードの管理記録を取得 | コードごとの管理記録から本支店IDを得て、該当する本支店本文だけまとめて取得 |

R2では他IDの使用中コードを拒否し、自IDの通常編集を許容する。変更前の管理記録を自分が所有することの確認、コード変更／無効化時の解放、再有効化時の確保を維持する。同一コードへ同時登録した場合は同じ管理記録の更新が競合するため、再判定して一方を拒否する。Functionsが順次実行されることには依存しない。

R3ではCSV内のコードを重複除去し、既存のまとめ読みを使う。管理記録の会社・コード全文・本支店IDを確認してから、本支店本文をID指定で読み、会社・コード全文・有効状態を照合する。不正なIDや管理記録不一致は採用せず、既存の行エラーとして扱う。事前確認と確定の両方で再取得し、既存の確認結果変更検知・全件棄却・再送制御を維持する。欠落時に全件検索で救済したり、取込み中に管理記録を補完したりしない。

### 方式を選ぶ理由

コード完全一致検索への置換も比較対象だが、本支店コードは確定仕様で桁数制限を撤廃済み。Firestoreの検索用項目は1,500バイト超で切り詰められ、その値を使う検索結果は不整合になり得るため、長いコードも許容する現仕様のまま全文検索へ依存しない。[Firebase公式制限](https://firebase.google.com/docs/firestore/quotas#indexes)（2026-10-13確認）。

検索用の短い追加項目を本支店本文に設ける案は、既存データへの追加が必要になる。既存管理記録を使う推奨案なら保存形式・既存IDを維持できる。コード上限の再導入、管理記録の新設、専用の準備印は提案しない。

### 削減量と影響範囲

工務店内の本支店数をB、CSV内の異なるコード数をKとする。R2は対象操作ごとのB件の全件取得を除去し、変更前後の管理記録は最大2件のまま。R3は本支店照合部分のB＋K件から最大2K件になる。CSVの行数ではなく異なるコード数に比例し、同じ本支店の行が多いほど効果がある。KがBに近ければ削減は小さい。不存在読取り、再試行、認証・会社・保証グループ・採番等を含む請求総量の見積りではない。実データ件数・費用削減率は未測定。

主な製品変更は上記Functionsの2ファイル。既存本支店ID・物件の所属・保証番号・CSV列・画面・Rules・索引は変更不要と見込む。共有Storeの承認済み全件キャッシュも維持する。先頭ゼロ、任意／条件付き必須、空コードの複数許容、同一工務店の有効本支店内だけの一意性、親無効化ではコードを解放しない仕様を維持する。

### 既存データと導入条件

導入前に、本支店と管理記録の対応を一度全件照合する。復旧時には `scripts/lib/recovery-controller.mjs` が既に有効・非空本支店と管理記録の件数・会社・全文・ID一致を検査する。初期取込の `scripts/lib/historical-intake-plan.mjs` も管理記録を生成する。これらと通常保存、Local初期データの生成経路を検証対象にする。導入前照合のために復旧処理全体を実行せず、同じ照合条件を読取り専用で利用する。

整合していればデータ移行は不要。不整合が見つかった場合だけ、対象・原因・必要な修正を報告し、明示された範囲で整備する。現時点では実データの不整合の有無は未確認であり、補完が必須とは判断していない。通常処理で黙って修復しない。

全件検索を撤去すると、管理記録を作らずに直接書き込まれた別本支店の重複を毎回発見する動作はなくなる。導入前照合と正規の登録・更新経路で一意性を維持する設計であり、アプリ外の直接書込みの整合性を保証しない既存の運用境界は維持する。整備・復元が必要な場合の既存利用制限も維持する。

保存形式は変えないので、本改修部分だけ旧取得方式へ戻す差戻しが可能。保証グループの末尾ハイフン等、別の確定変更を巻き戻さない。Dev導入は別途明示指示後。

### 検証条件

- 保存・コード変更・無効化・再有効化、他会社の同コード、同一会社の重複、空欄・必須、先頭ゼロ・長いコードを確認する。
- 独立2接続の同一コード同時登録と同時再有効化を反復し、一方だけ成立することを確認する。異なるコードは両方成立すること。
- CSVは同コード複数行、複数コード、管理記録欠落／不一致、無効本支店、事前確認後のコード変更／無効化を試験する。誤った本支店への取込みや部分登録を認めない。
- 無関係な本支店を追加しても保存の読取りが増えず、CSVは対象K件に対応する記録と本文だけを読むことを確認する。
- 初期取込・seed・復旧照合との整合、通常・結合・型・Functions構文・seed構文・文書の所定検証とLocal画面受入れを行う。実施結果は[運用記録](../operations.md)と[工程](../roadmaps/master-code-read-reduction.md)で管理する。[採用判断](../decisions/0044-branch-code-targeted-reads.md)。
