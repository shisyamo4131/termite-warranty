# Prod環境の初期構築・権限引渡し手順案

- 作成日：2026-10-02
- 状態：手順確認用。未実行。ProdプロジェクトID・HSアカウント・請求先・IAMの実値は未確認。
- 根拠：[ADR 0032](../decisions/0032-production-firebase-operations.md)、[HSC-020](../requirements/house-solution-confirmations/HSC-020-production-firebase-operations.md)。本書は既決定を具体化する案であり、追加権限・費用・作成を承認するものではない。

## 所有・アカウントの分離

HSが本番のプロジェクトと請求を管理し、開発者は自分のGoogleアカウントで作業する。Googleアカウントそのものへ開発者権限を付けるのではなく、Firebase/Google Cloudの対象プロジェクトにメンバーとして追加する。請求アカウントの権限、Google Workspace組織の管理権限、アプリ内のシステム管理者はそれぞれ別。

HSに会社管理のGoogle Workspace／Cloud Identityがあれば、その組織・管理者へ確認して利用する。既存アカウントが社長個人のGmailで私用データと混在している場合は、丸ごとの預託を標準にせず、HS管理の業務専用アカウントを検討する。新規Googleアカウントは既存の会社メールでも作成できるが、単なるGoogleアカウント作成だけで会社のWorkspace組織や組織的な回復管理が整うわけではない。回復用メール・電話・追加認証手段をHSが保持する。新規作成やログインでは本人確認が求められることがあり、パスワードだけで作業完了できるとは約束しない。

## 実行前にHSと揃えるもの

1. HSの担当者とアカウントの所有・回復担当。既存Workspaceの有無と外部開発者招待制限。
2. HSの請求名義・支払手段・費用の確認担当。カード情報は可能ならHS本人が入力する。
3. 開発者のGoogleアカウントのメール、必要な作業、初期構築の実施時間帯、暫定権限の終了条件。
4. 本番プロジェクト名／ID候補、公開URL・独自ドメインの要否。実際のIDは作成時に照合して記録する。
5. 本番DBの最終判断（HSC-022）。Firestore以外を選ぶ場合は以後のFirebase依存構築範囲を再検討する。

## HSが操作できない場合の実務手順

2026-10-02のユーザー決定：HS側アカウント設定は現地で行う。開発者はノートPCから本開発PCを遠隔操作し、Codexの支援を受ける。これは作業方式の決定であり、本番作成・課金・権限付与の実行完了を意味しない。

現地のノートPCでHS本人にログイン・追加認証を行ってもらい、開発者が設定を支援する。IAM付与後は本開発PC側で開発者自身のGoogleアカウントから対象アクセスを検証する。Codexが本開発PCから現地ノートPC上のブラウザを直接読めるとは扱わず、現地操作は開発者が行い、必要な非秘密の設定結果を共有する。秘密情報をチャットへ転記しない。当日前に遠隔接続・復帰・入力と通信を確認する。使用する遠隔操作製品や接続設定は未確認で、導入・設定変更は今回行わない。

HS本人にログイン・追加認証・支払確認だけ担当してもらい、開発者が同席または遠隔支援で設定画面を操作する方法が第一候補。HSにIAMの操作方法を習得してもらう必要はない。

一時的な秘密情報の預託で進める場合は、以下の順序とする（既存ADRが許容する初期構築限定の扱い）。

1. HSから対象アカウント、作業内容、費用を伴う操作範囲、預託期限について明示的な了解を得る。
2. 個人の私用アカウントよりHS管理の専用アカウントを選び、一時パスワードを設定する。HS側の回復手段は外さない。
3. 秘密情報はアクセス制限・期限付き共有などの安全な方法で開発者本人へ渡す。チャット、Git、手順書、メール本文やスクリーンショットに平文の秘密を保存しない。追加認証はその場でHSに対応してもらい、恒久的に開発者だけを回復先にしない。
4. 開発者端末は同期・パスワード保存を無効にした専用ブラウザプロファイルを使用。既存メールや他サービスへ不要にアクセスしない。HSのログインをCLIや自動配備の恒久認証にしない。
5. HS側で本番プロジェクトと請求を用意し、開発者アカウントをIAMへ追加する。
6. 開発者は別プロファイルで自分のGoogleアカウントへ切り替え、必要な操作を検証する。以後の通常保守ではHSアカウントを使わない。
7. HS側のアクセスが残ることを確認し、HSがパスワードを変更。借用端末のセッション・必要ならトークン等を失効し、共有リンク・保存物を削除する。単にパスワードを変えれば全セッションが必ず消えるとは扱わない。
8. 秘密を含まない引渡し記録を残す。実施者、対象、付与権限、確認日、預託終了、HS回復手段の保持確認を記録する。

## 実際の設定順序

| 段階 | 主体と操作 | 終了確認 |
| --- | --- | --- |
| 1 | HS本人の認証を支援し、HS所有の本番プロジェクトを新規作成／対象照合 | Devと異なるID、HSの管理アクセス |
| 2 | HS名義のCloud Billingを作成または選び、本番プロジェクトへ関連付け。Blazeを設定 | 請求担当・支払手段・通知先をHSが確認 |
| 3 | HSの権限でGoogle Cloudコンソールの対象プロジェクト→IAMと管理→IAM→アクセスを許可。開発者メールを追加して必要ロールを割り当てる | 開発者自身のログインで対象だけ操作可能 |
| 4 | 必要API、Authメール／パスワード、Webアプリ、Hosting、Functions、DBとRules/indexesを設定 | DB採用が確定済み。Firestoreなら東京asia-northeast1、Functionsも東京。DB所在地は作成前に最終確認 |
| 5 | 本番専用の配備認証・環境・対象確認を構成 | WIFを第一候補に検証。通常保守とCIの権限を分離、Devデータ・認証情報をコピーしない |
| 6 | アプリ内のシステム管理者・HS管理者を新規に作り、動作・アクセス範囲を確認 | クラウドIAMとは別管理。UIDと用途を台帳化、秘密は外部保管 |
| 7 | 監視、予算通知、バックアップ、Auth退避、復旧・差戻しを設定して検証 | ADR 0032の目標に対する実測結果を記録。未設定を完了扱いにしない |
| 8 | HSの受入確認後に利用開始 | 本番仕様、過去データ取込、採番開始値、運用担当が確定 |

請求先への関連付けはプロジェクト側だけでなく請求アカウント側の権限も必要。支払プロファイルの権限も別であり、Firebaseメンバー追加だけで請求管理をすべて委任できるとは扱わない。

## 権限付与の判断

HSが最終管理権限を保持。開発者へ永続的なOwnerを付けることを通常手順にしない。初期設定をHSセッションで代行した後は、Hosting、Functions、Firestore、Authentication、監視など必要作業に応じて権限を組み合わせる。Functionsの配備には実行サービスアカウントを使用する権限等も関係し、単一のFirebaseロールだけで足りるとは限らない。正確なロール一覧は実際の配備経路・組織制約と公式permission表を照合し、必要操作を試験して確定する。

通常保守にはプロジェクト削除権限を与えない。IAM変更・権限の再付与や、権限の強いサービスアカウントへのなりすまし経路も含めて確認する。「削除権限なし」と「業務データを壊せない」は同義ではないためバックアップと復旧検証を併用する。組織の外部招待制限がある場合は組織管理者に調整を依頼し、制限を勝手に無効化しない。

現段階は手順確認のみで、Prod構築・課金開始・秘密情報の受領は未実施。保険報告・更新の保留事項を自動実装する根拠にしない。
