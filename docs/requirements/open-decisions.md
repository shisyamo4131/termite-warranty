# Open Decisions

None of these items is a confirmed requirement or approved design decision.

## Product and Workflow

- The initial release requires case registration, master management, search/list views, and expiry alerts. Property, homeowner, construction company, responsible branch, and at least one applied warranty service with a warranty start date are required; selecting a property initially selects its homeowner and construction company, and staff may change either case value before saving. Cases receive an automatically assigned fixed-width sequential number, currently `000001` format, while legacy numbers are retained when available. The format may be revised after legacy-data inspection. What remaining field validation rules and acceptance criteria are required?
- The alert is displayed for an active case when any applied warranty is from 30 days before expiry through expiry, including after that applied warranty is `notified`; staff select `not notified`, `notified`, or `not required` per applied warranty. A case list/dashboard shows a `not notified` marker if any applied warranty is not notified, and a notification-status filter returns cases where any applied warranty matches. A warranty extension adds a new applied warranty to the same case, initially starting the day after the existing warranty expires; staff may change it and overlaps are permitted. Notification method, customer responses, and later timestamp/user attribution remain deferred.
- Account-management roles are developer superuser, House Solution administrator, and general staff. The developer superuser alone manages House Solution administrator accounts; House Solution administrators manage general-staff accounts and may edit email address, display name, and enabled/disabled state. The role is currently fixed to `general staff`; any future selectable role must exclude `House Solution administrator` and `developer superuser`.
- Construction-company form submission and provisional review are deferred. When resumed, which submission approach and review workflow will be adopted? See [external submission options](external-submission-options.md).

## Data and Migration

- House Solution retains the FileMaker data. Data is sought during September 2026 and the project will migrate records and fields to the extent feasible after inspection; complete historical migration is not required. CSV is the planned reception format, subject to confirming the actual FileMaker version, export permission, and exported table/field structure. Which records and fields will be provided, and when?
- The provisional model has separate branch, homeowner, property, construction-company, warranty-service, case, and applied-warranty records. A property has a required name plus homeowner and construction-company references. A case directly references its homeowner, construction company, property, and responsible branch; selecting or changing a property initially selects its homeowner and construction company, after which staff may change either case value before saving. Changing a property master's construction-company ID does not alter existing cases. Under the current provisional rule, a property-master homeowner change updates the homeowner ID of every case using that property, including a case with an independently selected homeowner; displayed names and address follow their masters. Decide whether a real ownership/company change should preserve existing case relationships while an explicit correction can selectively propagate, and whether the warranty-service payer or contracting party must be modeled separately from the property homeowner. Property address requires postal code, prefecture, municipality, and street/town and number; building name is optional. Responsible branch belongs only to a case, not to its construction company, homeowner, or property. A warranty-service master supplies a default period for newly added applied warranties; each applied warranty fixes that period but has an editable start date. Alert eligibility and notification status are held per applied warranty. Each applied warranty independently supports irreversible cancellation/invalidation with a free-text reason; a case can remain active even without an active applied warranty. Referenced masters are reversibly inactive rather than deleted, duplicate masters are allowed, and cancelled/invalid cases require a free-text reason, cannot be restored, and cannot be edited. What field rules, uniqueness constraints, relationships, and edit rules are required after legacy data is inspected?
- What feasible migration scope, data cleaning, recovery, and cutover procedure will be agreed after the data is inspected? Before cutover, House Solution confirms a migration report of migrated counts, unsupported or omitted items, and reasons. Temporary parallel operation is the initial safety direction, and evening/night final migration is acceptable; determine its duration, final data-freeze timing, and rollback decision.
- Postal code accepts seven digits with an optional hyphen and uses Japan Post's official Postal Code and Digital Address API on focus loss. For multiple town-area matches, auto-fill prefecture and municipality only, then let staff select or enter street/town and number. When no match or a business/other special postal code is returned, manual address entry is allowed; staff can correct auto-filled prefecture and municipality. On API failure, show an address-lookup failure message, retain input, and allow manual entry and saving. What agreement/credentials, availability/cost, and detailed address-validation rule will be selected?

## Technology and Operations

- What acceptance scope applies to the mandatory end-of-October 2026 production release?
- Nuxt SPA, Vuetify, Firebase Hosting, Firestore with an application-maintained 1- and 2-character N-Gram token map, Firebase Authentication email/password with browser-session persistence, and Cloud Functions for Firebase are adopted for the prototype. Exact local-prototype dependency versions are pinned in the manifest and lockfile; production promotion remains open. Development and production use separate Firebase projects; the development project is developer-owned and production ownership is under confirmation. The initial developer superuser is manually bootstrapped in Firebase Console without custom claims, using matching Firebase Authentication and enabled staff-account records. Cloud Functions with Firebase Admin SDK manages subsequent account creation/enable/disable and password setup/reset; Firestore requires an enabled staff account. Email-address verification is not initially required. Password emails use the standard Firebase Authentication delivery configuration initially; the actual rendered sender must be verified in development. What deployment configuration, transaction/retry/recovery, monitoring, production-package, and production-project ownership choices will be selected?
- Firestore remains subject to a production reassessment. What representative-data evidence, cost limit, response-time target, and schema/migration criteria would require PostgreSQL to replace it?
- The N-Gram normalization, token generation, and three-or-more-character AND-match rule are confirmed for construction-company, homeowner, and property master lists and their case-filter selection dialogs. What Firestore query/index design and update-consistency mechanism are required?
- When role-specific business-data restrictions are confirmed, will they need data-operation enforcement or only UI visibility? Account-management restrictions are already server-enforced; the current business-data posture is the same CRUD access for all enabled authenticated users.
- What security, privacy, availability, performance, support, and operating-cost requirements apply? Operation-history and audit-log records are excluded from the initial release.
