## Preparation

- Use Node.js 22, Java 21, and the exact npm version recorded in `packageManager`. Install with `npx --yes npm@11.19.1 ci`.
- Start `npm run emulators:start` in one terminal. Its npm lifecycle first runs the canonical `npm run prepare:functions` command and verifies the generated Functions domain copy. In another terminal, run `npm run emulators:seed`, then `npm run dev`. Direct Firebase CLI Emulator startup is not a supported prepared path.
- Dedicated local ports are Nuxt 23600, isolated UI workbench preview 23610, Auth 29099, Firestore 28080, Functions 25001, Emulator UI 24000, Emulator Hub 24400, and Emulator Logging 24500. These values are intentionally separate from the normal and Codex-test ports declared by the colocated `AirGuardV2` project; `AirGuardV2` keeps priority if a future conflict is discovered. Before starting either stack, inspect current listeners and do not retarget the other project.
- The seed is exact-endpoint- and `demo-*`-restricted and creates only synthetic names, dates, and the documented synthetic login. An unset Auth or Firestore Emulator host is assigned this project's dedicated endpoint; any different pre-existing value is rejected before Admin SDK initialization, including another loopback port. Do not add real homeowner, property, account, credential, or customer data.
- The browser client uses the Emulator only on `localhost` or `127.0.0.1`. On Firebase Hosting it loads the same-site `/__/firebase/init.json` configuration and refuses any project other than `termite-warranty-dev`; no Firebase Web API key is stored in source files.
- Build the Hosting artifact with the registered `npm run build` gate; for this static SPA it runs `nuxt generate` and produces `.output/public/index.html`. The GitHub Actions workflow `Deploy Firebase development` runs all seven comprehensive gates on pushes to `main` and on manual dispatch. Only an explicit `workflow_dispatch` can start the dependent deployment job. That job downloads the revision-bound Hosting artifact produced by the successful verification job, authenticates with the repository secret `FIREBASE_SERVICE_ACCOUNT_TERMITE_WARRANTY_DEV`, and deploys only to the explicit `termite-warranty-dev` target: `npx firebase deploy --project termite-warranty-dev --only firestore,functions,hosting --non-interactive`. It does not use `--force`; a required deletion, unsafe migration, minimum-billing increase, security change, or missing Artifact Registry cleanup policy fails closed for separate review and authorization. Configure an absent cleanup policy separately with the scoped Firebase Functions artifacts-policy operation before relying on unattended deployment; that external environment change is not performed by this repository workflow. On 2026-09-12, `npx firebase functions:artifacts:setpolicy --location asia-northeast1 --days 1 --project termite-warranty-dev --force` exited 0 and configured `gcf-artifacts` to delete container images older than one day. This policy concerns generated Functions container images only; it does not delete Firestore or application data. Do not create a default Firebase project alias. Development Functions use `asia-northeast1` and the SPA is served from `.output/public` with an `index.html` fallback. The service-account key is stored only as a GitHub Actions secret and must never be added to source control or logs. Before Functions deployment, Firebase predeploy invokes `npm run prepare:functions`; it stages and byte-verifies the shared modules from the sole authored `src/domain` source. The generated `functions/domain/` directory and temporary staging directories are never committed. Run `npm run check:functions-domain` for a read-only missing/extra/content-drift check.

This is technical smoke evidence, not House Solution acceptance. The seed creates only clearly named synthetic records, including six synthetic cases anchored to 2026-09-11 for local visual confirmation: two active alert cases, two active non-alert cases, one cancelled case, and one invalid case. Seed also rebuilds each synthetic case's parent list projection from its authoritative applied-warranty children. Because alert eligibility depends on the current date, rerun or intentionally revise the synthetic date set when this fixed anchor no longer exercises the alert UI. Unfiltered case and master screens show the freshest 20 records; dashboard totals and current search/filter controls apply only to that displayed window. Open each master from the Navigation Drawer to verify its list, detail link, detail-to-list return, shared edit dialog, and name filter; verify that inactive records remain readable. On a construction-company detail, verify its freshest 20 linked properties are listed, including an inactive one if present. On the dashboard, open active, cancelled, and invalid cases; verify applied-warranty details, terminal reasons, active-only edit availability, return links, and the in-app missing-ID state. Verify that construction-company creation/editing requires name and the first four address parts and preserves optional contact fields. On the dashboard, register a case from the dialog with application, handover, and warranty-start dates; verify that property selection initially selects both homeowner and construction company and that either can be changed. Optionally create one of the four supported masters without losing the case draft, verify the case row and alert marker, exercise the search filters, and repeat the same date/property-default/override checks while editing an active case. Edit a property's homeowner and construction company and confirm the existing case retains both references. Stop the emulator and development-server processes with Ctrl+C when finished.

Pre-change local emulator documents without the required company/homeowner address fields or case dates remain readable. A normal company or homeowner edit must fill the required postal code, prefecture, municipality, and street/town-and-number fields; optional building name, TEL, FAX, and notes remain nullable. Clearing and reseeding the disposable emulator is the simplest way to obtain a fully current synthetic dataset; this is not a production migration or backfill procedure.
